Every command has to be routed before it can be answered: handled locally, turned into a device action, or escalated to Claude. Two things here are settled — that the split between local and cloud is worth having, and how any router gets measured. The classifier currently doing the routing is not. It works, its costs are measured below, and it is flagged for replacement.

Decisions

01

The eval tests the classification task, not the classifier

{{ corpus.routing_cases }} routing cases and {{ corpus.conversation_cases }} context-dependent ones, written against the problem rather than the implementation — so the router can be replaced without losing the ability to compare before and after.

Each case is an input and an expected_route. Nothing in the corpus mentions keywords, embeddings, spaCy, tiers or thresholds, which means it is not a test of the current classifier and never was. A trained model, a local LLM or a function-calling router can be dropped in and scored on exactly these cases.

This is the decision that makes everything below replaceable. Coupling the eval to the implementation is the normal mistake — it produces a suite that passes right up until you change anything, and gives you no way to answer "is the new thing actually better". Architecture-agnostic cases are what buy measurement continuity across a rewrite.

The composition carries its own argument. adversarial and compound cases exist because a router that only sees well-formed single-intent commands will pass a suite and fail a house. The conversation set supplies history and then a fragment meaningless on its own — {% if corpus.sample %} routing "{{ corpus.sample.test_input }}" correctly requires knowing what was said immediately before it. {% endif %} Scenario files ({{ corpus.scenarios | join(', ') }}) chain commands the way a real morning or evening runs. A registry rule at the top of the file requires every new capability to add cases, so the target cannot widen without the tests widening too.

Write the eval against the task, not the solution. It costs nothing at the time and it is the only reason a planned rewrite is not also a restart on evidence.

The measured local layers span {% if cheapest and dearest %} {{ '%.3f'|format(cheapest.avg_ms) }} ms to {{ '%.1f'|format(dearest.avg_ms) }} ms {% endif %} — a wide spread in relative terms, and irrelevant next to the wall they exist to avoid. Even the most expensive local path is roughly {% if claude_ms and dearest %} {{ '{:,}'.format((claude_ms / dearest.avg_ms) | round | int) }}× {% endif %} cheaper than asking the model.

That ratio is why the tier concept stays on the roadmap even though the implementation does not. A replacement that is ten times slower at classifying but still local would barely register; one that gives up and escalates more often would be catastrophic for responsiveness. The metric that matters for any future router is escalation rate, not classification latency.

Know which number your architecture is actually defending. Here it is the round trip avoided, not the microseconds spent deciding — and that reframes what a replacement has to be good at.

Current implementation up for redesign

Routing is currently a hand-written cascade: keyword matching first, then spaCy parsing, then embedding similarity, escalating to Claude only when none of them can decide. It works and it is fast. It is listed here as the current answer rather than the settled one, because it does not scale.

What replaces it is open

Candidates under consideration, none decided:

  • A trained local classifier — learns the mapping instead of enumerating it, keeps latency in the local band.
  • A small local LLM parsing intent — handles unseen phrasing, at a latency cost that still avoids the network.
  • Auto-discovered intents via embeddings — derives the intent set from real usage rather than from what was imagined up front.
  • Routes defined as tools — a function-calling model routes internally, deleting the routing layer as a separate concern.

Whatever wins gets scored on the same {{ corpus.routing_cases }} routing cases and {{ corpus.conversation_cases }} conversation cases as the current cascade, which is the entire point of decision 01. The tier concept survives; the lookup tables do not.

What these numbers don't tell you

Routing accuracy has never been measured

The corpus defines {{ corpus.routing_cases + corpus.conversation_cases }} cases and tests/eval/results/ is {% if corpus.has_scored_results %}populated{% else %}empty{% endif %} — nothing has been scored against it. Everything on this page is latency, which says how fast a decision is made and nothing about whether it was right. That gap matters twice over here: without a baseline score for the current cascade, a replacement can be measured but not compared. Scoring the existing classifier is the prerequisite for the rewrite, not a follow-up to it.

The measurements are old, and the model has moved

Routing latencies are from {{ intent_run.timestamp[:10] if intent_run else 'April 2026' }}, and the Claude round-trip they are compared against is older still. Both the classifier and the model have changed since. The shape of the argument survives — a local match will always beat a network round trip — but the specific milliseconds should be re-measured before anyone quotes them.
