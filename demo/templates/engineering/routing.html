Every command has to be routed before it can be answered: handled locally, turned into a device action, or escalated to Claude. Two things here are settled — that the split between local and cloud is worth having, and how any router gets measured. The classifier currently doing the routing is not. It works, its costs are measured below, and it is flagged for replacement.

Decisions

01

The eval tests the classification task, not the classifier

{{ corpus.routing_cases }} routing cases and {{ corpus.conversation_cases }} context-dependent ones, written against the problem rather than the implementation — so the router can be replaced without losing the ability to compare before and after.

Each case is an input and an expected_route. Nothing in the corpus mentions keywords, embeddings, spaCy, tiers or thresholds, which means it is not a test of the current classifier and never was. A trained model, a local LLM or a function-calling router can be dropped in and scored on exactly these cases.

This is the decision that makes everything below replaceable. Coupling the eval to the implementation is the normal mistake — it produces a suite that passes right up until you change anything, and gives you no way to answer "is the new thing actually better". Architecture-agnostic cases are what buy measurement continuity across a rewrite.

This is the part of the design that survives whatever replaces the current classifier. The measured local layers span {% if cheapest and dearest %} {{ '%.3f'|format(cheapest.avg_ms) }} ms to {{ '%.1f'|format(dearest.avg_ms) }} ms {% endif %} — a wide spread in relative terms, and irrelevant next to the wall they exist to avoid. Even the most expensive local path is roughly {% if claude_ms and dearest %} {{ '{:,}'.format((claude_ms / dearest.avg_ms) | round | int) }}× {% endif %} cheaper than asking the model.

That ratio is why the tier concept stays on the roadmap even though the implementation does not. A replacement that is ten times slower at classifying but still local would barely register; one that gives up and escalates more often would be catastrophic for responsiveness. The metric that matters for any future router is escalation rate, not classification latency.

Know which number your architecture is actually defending. Here it is the round trip avoided, not the microseconds spent deciding — and that reframes what a replacement has to be good at.

Current implementation up for redesign

Routing is currently a hand-written cascade: normalize the phrasing, then keyword matching, then spaCy parsing, then embedding similarity, escalating to Claude only when none of them can decide. It works and it is fast. It is listed here as the current answer rather than the settled one, because it does not scale.

Tiers — what the command turned out to be the vertical axis: how far down it had to go
tiercoversanswered from
1 time and date questions the system clock — no device state, no model
2 device commands and status, plus the "good morning" / "good night" scenes in-memory device state, returned with its own [ACTION: ...] list
3 everything else — conversation, ambiguity, anything unrecognised Claude. This is the only tier that leaves the machine

Tiers 1 and 2 return their own response and stop; the model is never called. Tier 3 is not a match, it is the absence of one — what is left when no local layer could decide.

Layers — the mechanism that decided mostly Tier 2's internals, partly borrowed by Tier 1

Calling this a second axis flatters it. The full cascade belongs to Tier 2 — it is documented in the code as check_tier2's pipeline, and the tier list in the module header attributes the layer costs to the Tier 2 line specifically. Tier 1 borrows the two cheap rungs and skips the parse; Tier 3 has no layers at all, because it is not a match. Within a tier the rungs really are fallbacks: each runs only because the one above it declined. Across tiers they are not — Tier 1's keyword rung and Tier 2's are different code matching different tables, sharing a name and nothing else.

  • 0 · normalize — lowercases and strips filler prefixes (hey jarvis, could you please) before anything is matched against. It runs at the top of each tier, not once at the front, and it is the one rung with no row below: it decides nothing, so it is never what a result is attributed to. Bare can you is deliberately not stripped — it also opens questions, and removing it mid-sentence produces nonsense.
  • 1 · keyword match — regex and phrase lists over the normalized string. Handles the phrasings someone wrote down, in microseconds. In Tier 1 that means two narrow time/date patterns; in Tier 2, the ACTION_MAP and DEVICE_ALIASES tables.
  • 2 · dependency parse — spaCy recovers the verb from novel phrasing. Tier 2 only, and the one rung that is genuinely exclusive to it — there is no grammar worth parsing in "what time is it". It never touches the device — see the ceiling below.
  • 3 · embedding similarity — cosine against a labelled example set, as the last local resort before escalating. Each tier has its own set: eight canonical time/date phrases for Tier 1, twenty-nine device phrasings for Tier 2.

spaCy and sentence-transformers are optional dependencies. The module sets SPACY_AVAILABLE and EMBEDDINGS_AVAILABLE at import and disables those two layers if the packages are missing — so on a bare install the cascade is keyword-only and everything it used to catch falls through to Tier 3. That degradation is silent, which is defensible for a demo and would not be for a product.

How a command moves through it three probes, in order, each returning a finished answer or nothing
#probecatcheson no match
1 check_tier1 time and date returns None, falls through
2 check_context_commands "good morning" / "good night", time-gated returns None, falls through
3 check_tier2 device commands and status returns None, falls through
— — nothing left to try Tier 3. Claude is called

The Tier 3 result is an empty shell — confidence 0.0, response None, actions [] — built by falling off the end rather than by deciding anything. That emptiness is the interface: the orchestrator's test for "should I call the model" is simply whether the classifier came back with a response, so escalation needs no flag of its own.

Probe 2 is the odd one. It returns Tier 2 and stamps tier2_keyword, but runs before Tier 2 — the ordering is about its time gate, not its cost. "Good night" before 8pm and "good morning" outside 5am–noon deliberately return None and escalate, because at the wrong hour they are probably being said to a person, not to the house.

What each layer actually does
  • normalize — lowercase, then strip filler prefixes in a loop until none match, longest first, so stacked prefixes ("hey jarvis, could you please…") come off in one pass. A word-boundary guard stops a prefix eating a real word — without it please would strip the front of "pleased to meet you".
  • keyword — word-boundary regex, longest phrase first, over two tables: ACTION_MAP for verbs and DEVICE_ALIASES for devices. Longest-first is what makes "turn on" beat "on" and "bedroom light" beat "light"; matched in any other order the tables would silently mis-resolve.
  • dependency parse — takes the sentence root, then looks for a particle child (prt) to rebuild a phrasal verb: turn + on → turn on. Failing that it falls back to root.lemma_, which is what resolves "dims" → dim and "the fan should be switched off" → switch off — phrasings that appear nowhere in the tables.
  • embedding similarity — MiniLM, canonical phrases encoded once at import with unit norm, so the match is a plain dot product. It needs cosine ≥ 0.70 and returns None below that rather than the nearest label — a classifier with no I don't know would turn every unrecognised sentence into a device command.
Three places it refuses on purpose
  • The negation guard — any of don't, do not, never, won't and Tier 2 bails to Claude. Its position is the load-bearing part: after the status checks, so "is the fan not on?" still answers locally, but before action extraction, so "don't turn on the light" can never produce an action. Move it up and status queries break; move it down and the system acts on commands it was told not to.
  • Narrow Tier 1 patterns — the time regex carries a negative lookahead for a following "in", so "what's the current time in London" escalates instead of being answered confidently with the clock on this machine. The broad version of this pattern is the more obvious thing to write and it is wrong.
  • Entity-type validation — lights and switches accept only on/off, covers only open/close. "Open the fan" parses cleanly into a verb and a device and is still rejected, because the pair is nonsense. It escalates, so the apology comes from Claude rather than from a local error string.

All three refuse by returning None — the same thing "I didn't understand" returns. The cascade has one failure mode and it is always escalation; there is no path where it acts on a command it is unsure about.

The ceiling: the cascade only resolves the verb

Three layers deep sounds like three chances. It is three chances at the action only. Once a verb is found — by keyword, parse or embedding — the device is resolved by _extract_device, and that is a literal alias lookup with no fallback rung behind it. No spaCy, no embeddings.

"Turn on the heater" makes the asymmetry concrete. The verb resolves immediately — turn on is right there in ACTION_MAP — and the command still dies one line later, because heater is not an alias and the lookup returns None. "Shut off the kettle" gets its verb from two layers, keyword and parse agreeing, and dies the same way. Both escalate having been most of the way understood.

It also means matched_layer names how the verb was resolved, not how the sentence was — a row reading tier2_embedding still had its device matched by keyword, and always did.

This is the sharper version of the maintenance argument below. DEVICE_ALIASES is not merely one more hand-written table; it is the one table with nothing behind it, so every device phrasing nobody wrote down is a hard miss that no amount of semantic matching can recover. A replacement that resolves verb and device together is the actual requirement — and no candidate should be scored on verb accuracy alone.

What replaces it is open

Candidates under consideration, none decided:

  • A trained local classifier — learns the mapping instead of enumerating it, keeps latency in the local band.
  • A small local LLM parsing intent — handles unseen phrasing, at a latency cost that still avoids the network.
  • Auto-discovered intents via embeddings — derives the intent set from real usage rather than from what was imagined up front.
  • Routes defined as tools — a function-calling model routes internally, deleting the routing layer as a separate concern.

Whatever wins gets scored on the same {{ corpus.routing_cases }} routing cases and {{ corpus.conversation_cases }} conversation cases as the current cascade, which is the entire point of decision 01. The tier concept survives; the lookup tables do not.

What these numbers don't tell you

Routing accuracy has never been measured

The corpus defines {{ corpus.routing_cases + corpus.conversation_cases }} cases and tests/eval/results/ is {% if corpus.has_scored_results %}populated{% else %}empty{% endif %} — nothing has been scored against it. Everything on this page is latency, which says how fast a decision is made and nothing about whether it was right. That gap matters twice over here: without a baseline score for the current cascade, a replacement can be measured but not compared. Scoring the existing classifier is the prerequisite for the rewrite, not a follow-up to it.

The measurements are old, and the model has moved

Routing latencies are from {{ intent_run.timestamp[:10] if intent_run else 'April 2026' }}, and the Claude round-trip they are compared against is older still. Both the classifier and the model have changed since. The shape of the argument survives — a local match will always beat a network round trip — but the specific milliseconds should be re-measured before anyone quotes them.
