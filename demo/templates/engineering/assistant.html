This is the system the rest of the log is in service of. You speak or type, a routing cascade decides whether the question needs an LLM at all, Claude answers when it does, and the browser speaks the reply while the lights, fan and blinds change state.

Phase 1, running today against simulated devices. The hardware it is designed for — Zigbee bulbs, a mic array, wake word — is not bought yet, so device state lives in memory and resets when the server restarts. Everything below describes what the code does now, not what the deployment will do.

Decisions

01

The orchestrator owns device state, and re-shows it on every turn

The model is never asked to remember what it switched on. Current state is rebuilt into the prompt before every single request.

The tempting design is to let conversation history carry it: the model said "turning on the lamp" three turns ago, so it knows the lamp is on. That works until anything changes state outside the conversation — a physical switch, a scheduled routine, a restart, another client — at which point the model is confidently narrating a house that does not exist, and nothing in the transcript contradicts it.

So build_system_prompt() returns two blocks: a static one carrying the personality, the rules and the action format, and a dynamic one carrying the live device table. Only the second is rebuilt per request. The model is told, every turn, what is actually true, and instructed to answer status questions from that block rather than from the conversation.

Actions travel the other way as [ACTION: {...}] blocks parsed out of the reply, applied to the state dict, and stripped before the text reaches the browser. The model proposes; the orchestrator records. That split is what will let Home Assistant replace the in-memory dict later without the prompt changing at all.

If state can change behind the model's back, the model cannot be the thing that stores it. Re-showing the truth is cheaper than any scheme for keeping a transcript honest.

Reasoned, not measured. No experiment compares this against history-carried state — the argument is about a failure mode, and the failure mode is not one a latency table would show.

02

Voice I/O runs in the browser because it was fastest to ship — and it is not the destination

Both directions of speech are the browser's: speechSynthesis out, SpeechRecognition in. Zero server cost, zero added latency, nothing to install — and both are slated for replacement once there is hardware to replace them with.

The original build generated audio in Python: call a cloud TTS API, receive an mp3, write it to disk, load it, start playback. Every one of those is fast and all of them together are not — and the cost lands exactly where it is most visible, in the pause after the assistant has finished thinking.

speechSynthesis.speak() removes the whole chain. The browser's engine is already resident, so audio starts about as fast as the text arrives, and the server stops generating audio entirely.

Input went the same way for the same reason, and it turned out better than expected: Edge's integrated speech recognition is genuinely good — accurate enough on ordinary household commands that improving it has never been the bottleneck. Click the mic, talk, and it submits when you stop. That is a real capability acquired for roughly no engineering, which is the whole argument for taking it.

The trade is control and portability. Voice quality is the browser's opinion rather than ours — Edge is recommended for that reason — and none of it works headless, which is exactly what the eventual mini-PC deployment is. A box in a bedroom answering to "hey Jarvis" has no tab open, so a design that depends on one cannot be the final design. That was understood when the decision was made rather than discovered afterwards: docs/adr/002 scopes itself to the demo phase in its own consequences section and defers the production engine to a later ADR.

what it bought

A working voice loop in both directions, immediately, for no server cost, no added latency and no dependencies — on a project whose hardware had not been bought. Good enough is a real engineering result when the alternative is nothing to demo.

what replaces it

Server-side Whisper for STT and OpenWakeWord for "hey Jarvis", both in the hardware phase. TTS is the genuinely open one: local neural, cloud, or a speech-to-speech model that removes the conversion entirely.

None of that replacement is in progress. Whisper, the wake word and the mic array are roadmap items blocked on hardware that has not been ordered; no branch, no prototype, no benchmark. They are named here so the browser stack reads as a deliberate stopgap with a known exit rather than as the finished answer — but a plan with a dependency nobody has bought yet is a plan, and this page does not get to call it anything else.

Removing a step beats optimising it, and shipping the good-enough thing beats waiting for the right one — provided the swap is designed in rather than hoped for. What makes this a decision and not a shortcut is that the boundary was written down at the time.

Recorded in docs/adr/002-browser-tts-over-server-tts.md at decision time. 03

The wait is covered by speaking first, not by streaming harder

A Tier 3 answer costs {% if claude_ms %}about {{ '%.1f'|format(claude_ms / 1000) }} seconds{% else %}a couple of seconds{% endif %} of silence. The frontend fills it by asking a second endpoint for something to say.

Claude's reply is streamed internally but accumulated server-side before anything is returned, because actions have to be parsed out of the completed text before the browser is allowed to speak any of it — half a sentence read aloud with an [ACTION: ...] block still in it is worse than a pause.

So the browser calls /filler and /chat at the same time. /filler runs the same classifier, returns null for anything under Tier 3 — a local answer needs no cover, and "let me think" in front of an instant reply is worse than silence — and otherwise hands back a phrase from a pool keyed to the kind of thing that was said. The phrase is spoken while the model works.

Perceived latency and actual latency are different problems. This one is addressed where it is felt rather than where it is generated.

Unmeasured. Whether a spoken filler actually makes the wait feel shorter — or just makes the assistant seem to stall twice — is a question about people, and nothing here has asked one. The phrase pools are hand-written and their selection is random within a category.

04

Prompt caching was measured and rejected — but the first five results were lying

Six attempts, none faster. Five of them never turned caching on at all, and reported that as "no speedup".

Prompt caching should cut latency by reusing an already processed prefix — here, the static half of the system prompt, which is identical on every request. What has no measurement behind it unmeasured

Three of the four decisions above are arguments, not results

Only the caching experiment produced an artifact. The state design is reasoned from a failure mode, the TTS comparison is a decision-time record rather than a rerunnable benchmark, and the filler design has never been evaluated against anyone's actual perception of waiting. Each is labelled where it sits, and none of them should be read with the same weight as the detector or encoder tables elsewhere in this log.

The caching experiment is a single prompt

One command, {{ caching[0].runs_per_mode if caching else 10 }} runs per mode. Enough to show the mechanism engaged and produced no speedup at this context size; not enough to characterise caching in general, and it says nothing about token cost, which is the other reason to use it.

The interface was designed by taste

The dark theme, the six accent colours, the screensaver and its ten effects, the greeting, the personality in the system prompt — all chosen because they felt right for the thing being built. There is no A/B test, no preference study and no usability session behind any of it, and claiming otherwise would be the easiest way to make this page dishonest. They are listed because they are real parts of the product, not because they are defended.

"Edge's recognition is good" is an impression, not a number

It is stated above as a reason the browser stack was worth taking, and it is worth being clear about what backs it: daily use, and nothing else. Word error rate on this household's voices, accents and room acoustics has never been measured — there is no transcription benchmark in this repo, and no baseline to compare a Whisper deployment against when it arrives. Building one is part of what the swap is for.

Devices are simulated

Four entities — a main light, a lamp, a fan and blinds — live in a dictionary in the orchestrator process. They accept the same service calls Home Assistant will (light.turn_on, cover.open_cover and so on) so the prompt and the parsing do not have to change later, but nothing has ever been sent to real hardware. Latency, failure modes and partial state are all unknowns that only arrive with the Zigbee stack.
