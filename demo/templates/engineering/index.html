A record of the decisions behind the face pipeline — what was chosen, what was rejected, and what turned out to be wrong along the way. The benchmark tables exist and are linked, but the numbers are not the interesting part. The judgment calls are.

Every figure below is read from results/*.json when the page loads, so the arguments stand or fall on the current measurements rather than on numbers typed in once and left to rot.

Decisions

01

The development samples were biased, not noisy

Everything measured on 100-image slices had to be thrown out and re-run on the full datasets — 11,006 images instead of 300.

Sampling the first N images of WIDER FACE looks harmless. It is not: WIDER stores images grouped by event category (a parade, a courtroom, a beach), so a sequential slice does not sample the dataset — it samples one or two events. A hundred images of the same scene type is a hundred correlated observations, not a hundred independent ones.

The tell was that the error was systematic. Random noise moves detectors independently; a biased sample moves them together, because every detector is being asked the same wrong question. On WIDER FACE, going to the full set moved all four the same way at once — and on MAFA it moved three of the four the other way:

Note the direction flips between datasets. The WIDER sample was pessimistic and the MAFA sample optimistic — a sample being small does not tell you which way it lies. FDDB is the control: it barely moved, because it is stored as a flat list with no grouping for a sequential slice to land inside. That contrast is what makes this bias rather than bad luck.

A development sample is for checking that the code runs. It is not evidence, and it should never be the basis for choosing anything.

02

Two thresholds, two jobs — only one of them ships

The threshold used to compare encoders is not the threshold to deploy, and conflating them was a real bug here, twice.

TAR@FAR — the yardstick

Set by pinning every encoder to the same false-accept budget, then asking how many genuine faces it still admits. That shared budget is exactly what makes the comparison fair. It is a measuring instrument, chosen to hold one variable fixed across models — not a setting anyone should run.

max-F1 — the ship value

The cut-off that best balances precision against recall on the actual score distributions of this household. It answers a different question: not "which model is better" but "where should this model draw the line". This is what goes into the gallery.

For the winning encoder they are 0.214 and 0.342 — far enough apart that shipping the wrong one would be a real regression, close enough that nothing would obviously break. The benchmark now prints both, always labelled, and hands over the exact build command carrying the deployment value; a test asserts that command never carries the yardstick.

When one number ranks and another operates, name them differently everywhere — in the report, the config, the file format and the tests. Anything that prints a bare "recommended threshold" is a trap.

03

MediaPipe was eliminated for a failure mode, not for a score

It is the fastest detector measured by a wide margin, and it is fine on portraits. It was still ruled out — because where it fails is precisely where this system operates.

MediaPipe's BlazeFace downsamples the frame to 128×128 before detecting. On close, frontal faces that is plenty, and it scores respectably on FDDB. On WIDER FACE, where faces are small and crowded, it collapses to 0.07 AP — an order of magnitude below the others, not a few points.

That would be an acceptable trade for a phone app framing one face at arm's length. It is disqualifying for a doorway camera, because the moment that matters is someone standing back from the door, off to one side, occupying a small part of the frame. The regime MediaPipe is bad at is the deployment regime, so its 40 fps buys nothing.

"Worse on average" and "broken in the specific case you need" are different findings. Averages hide the second one, which is why the benchmark runs three datasets chosen to fail differently instead of one headline number.

04

The benchmark runs sequentially, and that is not an oversight

Parallelising the suite would cut a ten-minute run to a couple of minutes and make every latency number meaningless.

These are CPU-only models on a shared machine. Two detectors running at once contend for the same cores and the same memory bandwidth, so each one's measured per-image time becomes a function of what else happened to be scheduled beside it — unreproducible, and unfair in whichever direction the scheduler happened to lean. Wall-clock time is the cheap resource here; comparable numbers are the expensive one.

For the same reason only encoder.embed() and detector.detect() are inside the timed region. Model construction, weight downloads and image loading all sit outside it, so latency reflects inference rather than start-up.

A benchmark's job is comparability, not speed. Optimising the harness for throughput optimises away the thing it exists to produce.

What these numbers don't tell you

The detectors aren't emitting comparable kinds of output

YOLO is scored on a flood of candidates and the others are not. On the full WIDER FACE run:

YOLO proposes around {{ '%.0f'|format(box_rates[0].per_image) if box_rates else '290' }} boxes per image against RetinaFace's handful, because the harness asks it for everything at conf=0.0 so a full precision-recall curve can be swept. Its confidence floor therefore sits near zero, and the vast majority of those boxes are junk that any real threshold discards.

AP handles this correctly — it sweeps every cut-off, so low-confidence noise is priced in rather than ignored. But it is fair to say AP flatters a detector that is willing to guess. The stricter like-for-like read is F1 at each detector's own best threshold, where everyone is judged at a single operating point they actually have to commit to. YOLO wins on both, which is the reason the conclusion survives the caveat.

The recognition set is small and it is my family

Six people and 133 crops. That is enough to separate the household from 3,000 stranger comparisons, and not remotely enough to claim a general result about encoders. The numbers describe this gallery on these faces under this lighting; treat them as a configuration decision, not a finding.

An unrecorded setting nearly invalidated the detection threshold

The runs the shipped threshold rests on pre-date min_box_size being stored in the artifact. Re-running with it explicitly set to 0 produced a ground-truth count of 39,697 boxes on the same 3,226 images, against the 16,072 the original runs recorded — and AP fell for all four detectors at once, by up to 0.32.

The value was recovered by re-parsing the annotations at a range of filter sizes: only min_box_size = 20 reproduces exactly 16,072. So the original runs discarded faces under 20 px and never said so. That single unrecorded integer is the difference between an F1-max of 0.5727 and one of 0.2363 for the same detector on the same images.

Filtering at 20 px is the right call here — a face that small carries too few pixels for the recognition stage to encode, so detecting it would not help — but it has to be stated, because the threshold means nothing without it. It is recorded in every run from now on.
